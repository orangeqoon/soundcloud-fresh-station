# 既聴曲を飛ばすモードの実装計画

2026-10-24。v2.4.0で基本実装済みです。以下は実装仕様と、今後の拡張計画です。

## 実装した仕様

日本語の「Dig設定」に「一度でも聴いた曲を飛ばす」を追加しました。初期値はOFFです。チェックを入れると、**実際に再生位置が累計10秒進んだ曲**を既聴として扱います。曲IDが取れない曲、シークで飛ばした時間、停止中の時間は記録しません。

曲の切替、再生ボタン、play()の成功だけでは記録しません。音声のcurrentTimeの実際の進みを積み上げ、しきい値に達した時に1件保存します。シークで飛ばした時間、逆戻り、停止、通信待ち、エラー中の時間は加算しません。背景タブではイベント間隔が変わるので、単純に大きな差分を捨てず、シークイベント・経過時間・再生速度を照合します。OSの消音や本人が実際に聴いているかまでは判定できないため、技術的には再生履歴です。

数値のSoundCloud曲IDと通常のtrackであることを確認できた曲だけを対象にし、広告やID不明の曲をタイトル一致で記録しません。作者のページやライブラリから意図して聴く場合は、既聴による自動スキップを一時解除する設計を推奨します。そこで聴いた履歴自体は記録します。

## 保存とメモリ

- 正本はページ側のIndexedDB（FreshDig / heardTracks）です。IndexedDBが使えない場合だけ、同じ曲IDの最小記録をlocalStorageへフォールバックします。
- キーはアカウントIDと曲ID。値は初回既聴日時・判定ルールの版など最小限にします。曲名、画像、音声、認証情報は不要です。
- 全履歴を配列としてRAMへ読み込みません。タブごとに直近2,000件程度を上限とするLRUキャッシュを使います。
- 判定にない曲IDだけをIndexedDBで照会し、次のキュー候補は先読みします。未記録というキャッシュも、新たな記録の通知で無効化します。
- 複数タブからの記録はトランザクションで同じキーへまとめ、重複した履歴を作りません。アカウントが変わればメモリ上のキャッシュも切り替えます。
- 設定値だけは既存のchrome.storage.local同期経路に追加します。MAIN worldのプレイヤーからはbridgeとruntime messageを通して読み書きします。

メモリの上限は固定できますが、**正確な永久履歴のディスク容量は聴いた曲数に比例して増えます**。無制限で永久に正確な履歴と、保存容量の固定を同時には約束できません。初期案は勝手に古い履歴を削除せず、件数・容量の目安、履歴書き出し・読み込み、明示的な全消去、保存失敗の通知を用意します。期間や件数制限を選ぶ場合は、古い曲が再び流れ得ることを表示します。未聴曲を誤って除外するBloom filterは初期案では使いません。

ブラウザーのデータ消去、拡張の削除、保存領域の問題で履歴を失う可能性があります。容量は実ブラウザーで測定し、IDのバイト数だけから見積もりません。

## 曲が始まる前の判定

現在の除外判定は同期処理ですが、IndexedDBは非同期です。まずキューの先読みと固定サイズのキャッシュで大半を処理します。履歴が未照会のまま曲が始まる場合の方針は、実装前に決める必要があります。

推奨は、ローカル照会に短い上限を置き、失敗時は曲を流して不具合レポートへ残す方式です。未聴曲を誤って飛ばすことを避けます。先読みが間に合わない場合に短い音が出る可能性まで完全に排除するには、SoundCloud内部の再生開始処理との追加調整と実機検証が必要です。今回見つかった通信待ちの不具合を繰り返さないよう、単なる照会待ちやタイムアウトで音声を勝手に停止させません。

## 実装の順番

1. 既聴とする秒数、作者ページでの例外、容量・削除方針を確定する。
2. 音声の実再生時間の集計を作る。DOM外のnew Audio()も含め、シーク・通信待ち・背景タブをテストする。
3. アカウント別IndexedDBとbridge、複数タブの重複防止を実装する。
4. キュー先読み・LRU・照会失敗時の動作を実装する。
5. Dig設定、件数表示、履歴の削除・入出力・失敗表示を追加する。
6. 長時間再生、広告、タブ破棄、アカウント切替、容量不足、実際のEdge/Chromeで検証する。

## リストのバックアップとの関係

今回の4種類のリストは、Markdownが閲覧用、JSONが復元用です。既聴曲の履歴は件数が大きくなるため、将来は別のスキーマ・ファイルに分けます。大量の履歴を一度にJSON文字列化するとRAMを使うので、ページ単位・分割ファイルなどの入出力方法も用意します。

JSONバックアップがあれば、SoundCloudのプレイリストへの保存はバックアップ目的では必須ではありません。既存のNoPlayプレイリスト連携は任意の手動機能として残し、不要なら後の整理で畳む・削除するのがよいと考えます。JSONを読み込んでもSoundCloudのLikeやFollowを書き換えません。
